# AG-004 — Project-scoped authorization and viewer sharing

Status: implemented for the owner/viewer vertical slice; the production capacity gates in
[`docs/scaling.md`](../scaling.md) remain unverified until an Oracle-backed staging run.

AG-004 treats `Dashboard` as the security boundary. A grant is an explicit relationship between
one Dashboard and one canonical SOEID. It grants only read-only Viewer capability for the exact
Revision pinned by that Dashboard while it is Published. It never grants a draft, an arbitrary
Revision, owner controls, or access to another Dashboard.

## Policy matrix

| Principal | Project metadata and discovery | Dashboard-package delivery | Management and mutations |
|---|---|---|---|
| Active owner | Own non-deleted Dashboards; owner detail and access page | Owner preview for an exact complete Revision; published view | Full control for own Dashboard; current slice covers upload, grant list, grant, and revoke, while lifecycle routes remain separately gated |
| Active granted Viewer | Shared with Me contains only currently Published Dashboards with an active grant | Only the current `published_revision` and its HTML plus Supporting Artifacts; every request is rechecked | No upload, preview, access-management, publication, or other owner action |
| Revoked Viewer | No longer listed in Shared with Me; an external project resolves generically as not found | Existing render credentials fail on the next package authorization check | No project controls; retained revoked epoch is visible only in the owner's bounded history |
| Active unrelated user | Cannot enumerate another user's project, grants, revisions, or history; generic 404 behavior | Denied, including altered Dashboard, Revision, filename, or storage-key identifiers | No management or mutation rights |
| Administrator without ownership or grant | No implicit Dashboard content or metadata access | Denied exactly like another unrelated user | No Dashboard management rights from administrator status alone |
| Disabled user | Authentication and project resolution fail closed; retained grants remain auditable by the owner and are shown as disabled | Denied, even if a grant row remains unrevoked | No management or mutation rights |
| Unauthenticated request | Redirected to authentication by portal routes; no project enumeration | Denied by the content authorization boundary | No management or mutation rights |

Disabling a Dashboard owner removes that owner's personal management/viewing access but does not
implicitly unpublish the Dashboard or revoke active access for other active granted viewers.

Grant management accepts only a canonical SOEID resolved through the identity boundary. Invalid,
unknown, disabled, self, active-duplicate, and concurrent-create-lost cases return safe form
messages without disclosing another user's project relationship. Revoke is an owner-only,
CSRF-protected POST with explicit destructive confirmation. It is idempotent for retries and
retains the closed grant epoch and audit event.

## Query and data guarantees

- Owner lookups scope by `(dashboard_id, owner_id)` and return a generic `None`/404 result for a
  missing or unrelated project.
- Revision, current-grant, and retained-history querysets are lazy, deterministic, and safe to
  slice before evaluation. Artifact metadata is prefetched only for the bounded revision page
  that needs it; uploaded bytes never enter portal templates.
- The owner viewer count is a database `COUNT` over unrevoked grants whose target User is active;
  it does not materialize grant rows or retained history.
- Shared with Me uses an existence check for the exact active grant and therefore stays
  duplicate-free when revoked grant epochs are retained. Current grant and viewer lookup indexes
  support both Dashboard-to-viewer authorization and viewer-to-project discovery.
- Every grant/revoke event records actor, target user, Dashboard, action, and timestamp in the
  append-only audit stream.

Migration `0011_project_viewer_epochs` can be reversed only before any Dashboard/viewer pair has
more than one retained epoch. After a revoke/regrant cycle, restoring the former lifetime-unique
constraint deliberately fails rather than deleting audit history; operators must roll forward or
restore a pre-migration backup instead of deduplicating epochs.

## Revocation and publication guarantee

The content resolver rechecks User active state, the exact Dashboard grant/ownership, Published
state, the pinned published Revision, token expiry, and token revocation for every package
authorization check. Thus a revoke, disable, or unpublish denies the next check even when a
short-lived render credential was issued earlier. Bytes already streamed to a browser cannot be
recalled; operators must treat any previously delivered bytes as copied by the recipient.

## Verification evidence

`tests/test_project_queries.py` covers owner scoping, generic misses, lazy bounded revision pages,
select-related current/history rows, database counting, deterministic ordering, duplicate-free
Shared with Me results after revoke/regrant, disabled-user filtering, and query-count regressions.
The integrated AG-004 gate additionally covers grant/revoke lifecycle, concurrent duplicate
safety, CSRF and method restrictions, draft/unpublished isolation, exact pinned package delivery,
render-credential invalidation, and the complete matrix above. Oracle-backed integration and
browser tests must pass before release; a passing unit suite alone is not evidence of
thousands-user capacity.
